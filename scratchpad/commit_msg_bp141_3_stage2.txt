KN-BP141-3 Stage 2: Elimination Cascade with Bidirectional Consistency

New file C:\Users\Administrator\Documents\mnemosyne\src\main\plow\plow_mc_elimination_cascade.ts.
Encodes the Founder's five-stage elimination procedure (C1-C5) as pure,
synchronous helpers. This module never queries a model, browser, or any
external source itself -- exactly like solveNoConsensusFromScatter's own
IndependentSourceVote convention in plow_mc_no_consensus_solver.ts, it only
ever consumes caller-supplied rankings/votes and applies the Founder's own
consistency/acceptance math to them. The actual dispatch of a most-to-least
or least-to-most ranking QUERY to a live source, and the pipeline wiring that
would let C1-C5 decide a live answer inside plow_mc_answerer.ts, does not
exist yet -- documented as an honest gap below, same convention as the Cake
Method's own "live mesh-peer transport not wired" gap already in that file.

C1 ASK THE INVERSE (detectNegationQuestion, buildInverseQueryFraming):
detects an explicit NOT/EXCEPT polarity qualifier in a stem (narrow regex,
requires the negation to sit directly on a copula/modal verb, not merely
"not" occurring anywhere in the prose) and builds the mechanical, reversible
complement framing a caller can query instead, to sidestep the
negation-blindness that trips models on NOT/EXCEPT questions (191 in the
dataset per the ticket).

C2 JAR METHOD (orderEliminationBlocksByCertainty): pure sort of
caller-supplied elimination blocks, descending certainty first, descending
block size as tiebreaker -- "softballs out before marbles". Does not itself
decide whether to apply any block, only the order to consider them in.

C3 CAKE CUT HALF, ALTERNATING (generateCakeCutAlternatingSplits): pure split-
plan generator over the currently-surviving option letters -- pass 1 asks
about the first half, pass 2 asks about the second half (direction
inverted), pass 3 is a control pass re-including the first half alongside
the second half to catch a source flip-flopping on an option it had just
claimed was eliminable.

C4 BIDIRECTIONAL CONSISTENCY (checkBidirectionalConsistency,
runBidirectionalConsistencyGate) -- the strongest gate in this file. Requires
a source's own least-to-most ranking to be the EXACT element-wise reverse of
its own most-to-least ranking (same letters, same count, reversed order, not
merely the same set). Reports every mismatched position by index, never a
bare true/false, so a failure is inspectable. runBidirectionalConsistencyGate
partitions sources into admissible/inadmissible and never averages or
discounts a failure -- an inconsistent source's ranking is excluded entirely,
per the ticket's own "FAILURE = that source's ranking is inadmissible".

C5 TERMINATE ON THE NUMBER (determineRequiredPrecision,
evaluateSignificantFigureAccept): the significant-figures accept condition.
Required precision is derived from the option set's OWN spacing (half the
smallest gap between any two distinct sorted option values), never from a
fixed arbitrary tolerance. Accepts a computed value only when it lands
closer to one option than the required precision AND the winning margin over
the second-nearest option also clears that same precision -- never demanding
more digits than the option set's own discrimination requires, never forcing
an accept when the computed value sits ambiguously between two options.
